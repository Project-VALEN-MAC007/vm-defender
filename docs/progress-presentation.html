1. ภาพรวมและเป้าหมายของระบบ (1.5 นาที)

ปัญหาที่ต้องการแก้

Honeypot แบบดั้งเดิมมีข้อจำกัดสำคัญคือ ทำงานแบบตายตัว ผู้โจมตีจะถูกส่งไป honeypot หรือไม่ถูกส่ง ตัดสินใจครั้งเดียวจบ ทำให้เกิดปัญหาสองด้าน

ถ้าตั้งเข้มเกินไป ผู้ใช้ปกติถูกส่งไป honeypot โดยไม่จำเป็น (false positive) ถ้าตั้งหลวมเกินไป ผู้โจมตีเข้าถึงระบบจริงได้ (false negative)

แนวคิดของระบบนี้

ระบบ Adaptive Honeypot ที่พัฒนาขึ้นใช้หลักการ ให้คะแนนความเสี่ยงแบบสะสม และเปลี่ยนเส้นทางตามระดับคะแนน แทนการตัดสินครั้งเดียว

หลักการทำงานคือระบบจะเฝ้าดูพฤติกรรมของแต่ละ IP ต่อเนื่อง สะสมคะแนนเมื่อพบ พฤติกรรมน่าสงสัย และลดคะแนนลงเมื่อเวลาผ่านไปโดยไม่มีพฤติกรรมผิดปกติเพิ่ม เมื่อคะแนนถึงเกณฑ์จึงเปลี่ยนเส้นทางไป honeypot ที่เหมาะสมกับประเภทการโจมตี

สิ่งที่ทำให้ระบบนี้แตกต่าง

การเชื่อมโยงข้ามโปรโตคอล (cross-protocol correlation) คือจุดเด่นหลัก ระบบจดจำว่า IP หนึ่งเคยสแกนพอร์ตมาก่อน เมื่อ IP เดิมกลับมาเรียกเว็บ จะได้คะแนนเพิ่ม 20 คะแนนทันที เพราะพฤติกรรม "สแกนแล้วเข้าเว็บ" น่าสงสัย กว่าการเข้าเว็บเปล่าๆ อย่างชัดเจน

การลดคะแนนตามเวลา (decay) ป้องกันการลงโทษถาวร ระบบลดคะแนน 1 คะแนน ต่อนาที ทำให้ IP ที่เคยทำผิดพลาดครั้งเดียวกลับมาใช้งานปกติได้เอง ไม่ต้องรอผู้ดูแลปลดบล็อกด้วยมือ

2. สถาปัตยกรรมและการทำงาน (2 นาที)

โครงสร้างเครือข่ายสามชั้น

ระบบออกแบบให้ Defender เป็นตัวกลางระหว่างผู้โจมตีและ honeypot โดย ผู้โจมตีไม่สามารถเข้าถึง honeypot ได้โดยตรง

┌─────────────┐         ┌──────────────────────┐         ┌──────────────┐
│  Attacker   │         │      DEFENDER        │         │  Honeypot    │
│    VM       │────────▶│                      │────────▶│     VM       │
│             │  outer  │  Suricata (ตรวจจับ)  │  inner  │              │
│192.168.56.x │ network │  Decision Engine     │ network │  10.10.10.2  │
└─────────────┘         │  Nginx / nftables    │         │              │
                        │                      │         │ WordPress    │
                        │ outer: 192.168.56.10 │         │ phpMyAdmin   │
                        │ inner: 10.10.10.1    │         │ Cowrie SSH   │
                        └──────────────────────┘         └──────────────┘

เหตุผลที่แยกเป็นสองเครือข่าย คือถ้าผู้โจมตีหลุดออกจาก honeypot ได้ จะไม่สามารถย้อนกลับไปโจมตีเครือข่ายของผู้โจมตีเองหรือออกอินเทอร์เน็ต เพราะเครือข่าย inner ตั้งค่าเป็น isolated ไม่มี default route

ลำดับการทำงานเมื่อมีการโจมตี

1. ผู้โจมตีส่ง request  →  เข้า Defender ทาง outer interface
                              ↓
2. Suricata ตรวจจับ    →  เขียน alert ลง eve.json (JSON บรรทัดต่อบรรทัด)
                              ↓
3. Decision Engine อ่าน  →  แปลง alert เป็น event ที่มีรูปแบบมาตรฐาน
                              ↓
4. คำนวณคะแนนเสี่ยง    →  บวกคะแนนตาม severity + protocol + ประวัติ
                              ↓
5. เทียบเกณฑ์          →  ต่ำกว่า 15 ปล่อยผ่าน / 15-40 เฝ้าดู
                          40-80 เปลี่ยนเส้นทาง / เกิน 80 บล็อกชั่วคราว
                              ↓
6. สั่งการ              →  เว็บใช้ Nginx map / SSH ใช้ nftables DNAT
                              ↓
7. บันทึกหลักฐาน       →  decisions.jsonl + แสดงบน Dashboard

D6 — Decision Engine (ส่วนที่สมบูรณ์ที่สุด)

โครงสร้างโค้ดแบ่งเป็น 8 โมดูล แต่ละโมดูลรับผิดชอบงานเดียว

ไฟล์หน้าที่
reader.pyอ่าน eve.json ต่อเนื่อง จัดการ log rotation
models.pyโครงสร้างข้อมูล Event และ Decision
risk.pyคำนวณคะแนนเสี่ยง จัดการ decay และประวัติ
engine.pyตรรกะหลัก ประสานงานทุกส่วน
adapters.pyสั่ง Nginx และ nftables
config.pyโหลดและตรวจสอบค่าตั้งต้น
cli.pyจุดเริ่มโปรแกรม รองรับ dry-run

ความสามารถที่ทดสอบแล้วว่าทำงานถูกต้อง

การอ่าน log แบบต่อเนื่องใช้ระบบ checkpoint บันทึก inode และตำแหน่ง byte ทำให้เมื่อโปรแกรมหยุดแล้วเริ่มใหม่ จะอ่านต่อจากจุดเดิมไม่ซ้ำและไม่ข้าม และรับมือกับการที่ Suricata หมุนไฟล์ log ได้โดยตรวจจับจาก inode ที่เปลี่ยน

การป้องกันการนับซ้ำใช้ SHA-256 hash ของเนื้อหา event เป็นตัวระบุ ถ้า event เดิมถูกอ่านซ้ำ ระบบจะข้ามไปโดยไม่บวกคะแนนเพิ่ม

การเขียนไฟล์ config ของ Nginx ใช้วิธี atomic write คือเขียนลงไฟล์ชั่วคราว ก่อน แล้วใช้ rename ซึ่งเป็น operation ที่ระบบไฟล์รับประกันว่าเสร็จหรือ ไม่เสร็จเท่านั้น ไม่มีสถานะกลาง ป้องกัน Nginx อ่านไฟล์ที่เขียนไม่เสร็จ

การกู้คืนเมื่อผิดพลาด ถ้า nginx -t ตรวจว่า config ใหม่ผิด ระบบจะคืนไฟล์ เดิมกลับทันทีและไม่ reload มีเทสต์ยืนยันว่าเนื้อหาไฟล์กลับเป็นค่าเดิม แบบตรงตัวอักษร

D7 — Dashboard (ปรับปรุงล่าสุด)

Dashboard แสดงข้อมูลสองส่วนคือ Suricata alerts และ Decision Engine logs ผูกกับ 127.0.0.1 เท่านั้น มีการตรวจสอบในโค้ดที่ปฏิเสธการผูกกับ IP อื่น

สิ่งที่แก้ไขในรอบล่าสุด เดิม tab แสดง alerts สร้างข้อมูลขึ้นเองจาก decisions ซึ่งไม่ถูกต้องเพราะไม่ใช่ alert จริง ได้แก้ให้อ่านจาก eve.json โดยตรง parse เฉพาะ event ที่มี event_type เป็น alert และดึงค่า signature, category, severity, IP, port จาก event จริงเท่านั้น

ถ้าไฟล์ไม่มีหรืออ่านไม่ได้ ระบบจะข้ามไปเงียบๆ ไม่สร้างข้อมูลปลอมมาแทน

API endpoints ที่มี

Endpointผลลัพธ์

/api/alerts.csvดาวน์โหลด alerts เป็นไฟล์ CSV
/api/decisions.jsonการตัดสินใจของ engine
/api/decisions.csvดาวน์โหลด decisions เป็นไฟล์ CSV

การ export ส่ง HTTP header Content-Disposition: attachment ทำให้ เบราว์เซอร์ดาวน์โหลดเป็นไฟล์แทนการแสดงเป็นข้อความ ยืนยันด้วย curl -OJ ว่าไฟล์ถูกเขียนลงดิสก์จริง

D8 — ระบบตรวจสอบก่อนนำ rule ใหม่เข้าใช้

ออกแบบให้ rule ใหม่ที่ได้จากการวิเคราะห์ honeypot ต้องผ่าน 5 ประตู ตรวจสอบ ก่อนถูกนำเข้าระบบจริง

ประตูตรวจอะไรผลการทดสอบ
1syntax ถูกต้อง Suricata อ่านได้✅ ผ่าน
2SID ไม่ซ้ำและไม่ทับซ้อน rule เดิม✅ ผ่าน
3ไม่ทำให้ false positive เพิ่ม✅ ผ่าน FPR = 0.0
4ตรวจจับการโจมตีที่ควรตรวจจับได้✅ ผ่าน พบ 2 รายการ
5ประสิทธิภาพไม่ตกต่ำกว่าเกณฑ์✅ ผ่าน

ผลการทดสอบวงจรครบรอบ จาก evidence/test-results/feedback-loop-report.json

{
  "expected_sid": 2200401,
  "alert_count": 1,
  "detected_next_attack": true,
  "replay_exit_code": 0,
  "host_service_reloaded": false,
  "deploy": { "status": "deployed", "reviewer": "lab-reviewer" }
}

ลำดับที่ทดสอบคือ นำหลักฐานจาก honeypot ที่ปิดข้อมูลอ่อนไหวแล้ว มาสร้าง rule ใหม่ SID 2200401 ผ่านการตรวจ 5 ประตู นำเข้าใช้แบบชั่วคราว แล้ว replay การโจมตีรูปแบบเดิมอีกครั้ง ระบบตรวจจับได้ ยืนยันว่าวงจรการเรียนรู้ ทำงานครบรอบ

ค่า host_service_reloaded: false แสดงว่าไม่ได้แตะ service จริงบนเครื่อง เป็นการทดสอบในพื้นที่แยกทั้งหมด

การทดสอบการกู้คืน ทดสอบกรณี health check ล้มเหลวหลัง deploy ระบบเปลี่ยนสถานะเป็น rolled_back และคืนไฟล์ rule เดิมกลับ ตรวจสอบแล้ว ว่าเนื้อหาตรงกับค่าเดิมแบบตรงตัวอักษร

5. อุปสรรคและแผนต่อไป (1.5 นาที)

อุปสรรคที่ 1 — ขาด network interface

VM ปัจจุบันมี network interface เพียงตัวเดียวคือ enp0s3 ซึ่งเป็น VirtualBox NAT ถือ IP 10.0.2.15/24 และเป็นเส้นทางเดียวที่ออกเน็ตได้

ระบบต้องการเพิ่มอีก 2 interface สำหรับเครือข่าย outer และ inner

สิ่งที่ตัดสินใจไม่ทำและเหตุผล ทางเลือกที่ง่ายคือกำหนด IP 192.168.56.10 และ 10.10.10.1 ลงบน enp0s3 ที่มีอยู่ แต่เลือกไม่ทำ เพราะจะทำให้เครือข่ายจัดการ เครือข่ายผู้โจมตี และเครือข่าย honeypot รวมอยู่ที่เดียวกัน ซึ่งทำลายหลักการแยกส่วนที่เป็นหัวใจของระบบ

ถ้าผู้โจมตีหลุดจาก honeypot จะเข้าถึงเครือข่ายจัดการและออกอินเทอร์เน็ตได้ เท่ากับสร้างช่องโหว่จริงขึ้นมาเอง จึงบันทึกเป็น BLOCKED และรอแก้ที่ต้นเหตุ

วิธีแก้ ปิด VM เพิ่ม Internal Network adapter 2 ตัวใน VirtualBox Manager แล้วเปิดเครื่องใหม่ ตรวจชื่อ interface จริงก่อนกำหนด IP ขั้นตอนละเอียดอยู่ใน defender/network/virtualbox-nic-checklist.md

อุปสรรคที่ 2 — ไม่มีสิทธิ์ sudo

ผู้ใช้ yakult อยู่ในกลุ่ม sudo แต่คำสั่ง sudo -n true แจ้งว่า ต้องใส่รหัสผ่าน ซึ่งยังไม่ได้รับ

งานที่ทำไม่ได้เพราะเหตุนี้คือ ติดตั้ง Nginx, Git และ conntrack ตรวจสอบและแก้ไข nftables ruleset กำหนด IP ให้ interface เปิด IP forwarding รีสตาร์ท Suricata และอ่าน /var/log/suricata/eve.json

คำสั่งทั้งหมดที่ต้องใช้ sudo รวบรวมไว้ใน docs/root-operations.md แล้ว พร้อมขั้นตอนกู้คืนกรณีผิดพลาด เพื่อให้เจ้าของเครื่องตรวจสอบก่อนรัน

อุปสรรคที่ 3 — รอข้อมูลจากคนที่ 2

ระบบต้องรู้ค่าจริงของ honeypot จึงจะเชื่อมต่อได้ ค่าที่ยังไม่ได้รับคือ

ข้อมูลใช้ทำอะไร
IP และ interface ของ honeypotกำหนดเส้นทาง
port และ health path ของ WordPressตรวจสุขภาพ backend
port และ health path ของ phpMyAdminตรวจสุขภาพ backend
port และ log path ของ Cowrieตรวจสุขภาพและอ่าน log
return routeให้ traffic กลับได้

ข้อกำหนดรูปแบบข้อมูลเขียนไว้ใน docs/person2-contract.md เป็น JSON schema เพื่อให้ส่งข้อมูลมาในรูปแบบที่ระบบใช้ได้ทันที ระบบตั้งค่าตั้งต้นไว้ว่า ไม่ถือว่า endpoint ใดพร้อมใช้งานจนกว่าจะได้รับค่าจริงและตรวจสอบแล้ว

ประเมินความคืบหน้า

ส่วนที่เป็นซอฟต์แวร์ซึ่งควบคุมได้เอง เสร็จและทดสอบแล้วประมาณ 85% ส่วนที่เหลือขึ้นกับ infrastructure และข้อมูลจากทีม ไม่ใช่ตัวโค้ด

งานที่เตรียมไว้พร้อมใช้ทันทีเมื่ออุปสรรคถูกแก้คือ template ทุกไฟล์ ขั้นตอนกู้คืน checklist และชุดทดสอบ ทำให้เมื่อได้ sudo และ NIC แล้ว สามารถดำเนินการต่อได้เลยโดยไม่ต้องเขียนโค้ดใหม่

ภาคผนวก — คำถามที่คาดว่าจะถูกถามและคำตอบ

หมวดที่ 1 — คำถามเรื่องความคืบหน้า

ถาม: ทำไมหลายเฟสยังไม่เสร็จ

ตอบ: งานส่วนซอฟต์แวร์เสร็จหมดแล้วครับ ที่ยังไม่เสร็จคือส่วนที่ต้องติดตั้ง บนเครื่องจริง ซึ่งติดขัดสองเรื่องที่อยู่นอกเหนือการควบคุม คือ VM ยังไม่มี network interface ที่ต้องการ และยังไม่ได้รับรหัส sudo

ถ้าเทียบเป็นสัดส่วน โค้ดและการทดสอบเสร็จประมาณ 85% ส่วนที่เหลือคือ การนำไปติดตั้งซึ่งใช้เวลาไม่นานเมื่ออุปสรรคถูกแก้ เพราะเตรียม template และขั้นตอนไว้ครบแล้ว

ถาม: ทำไมไม่กำหนด IP ที่ต้องการลงบน interface ที่มีอยู่ไปเลย

ตอบ: ทำได้ทางเทคนิคครับ แต่จะทำลายหลักการแยกเครือข่ายที่เป็นหัวใจของระบบ

ถ้ารวมทุกเครือข่ายไว้ที่ interface เดียว เครือข่ายจัดการ เครือข่าย ผู้โจมตี และเครือข่าย honeypot จะอยู่ที่เดียวกัน กรณีที่ผู้โจมตีหลุดจาก honeypot ได้ จะเข้าถึงเครือข่ายจัดการและออกอินเทอร์เน็ตได้ทันที เท่ากับสร้างช่องโหว่จริงขึ้นมาเอง

จึงเลือกบันทึกเป็น BLOCKED และรอแก้ที่ต้นเหตุ ซึ่งใช้เวลาเพียงไม่กี่นาที คือปิด VM แล้วเพิ่ม adapter

ถาม: 85% วัดจากอะไร

ตอบ: วัดจากจำนวนโมดูลที่เขียนเสร็จและมีเทสต์ครอบคลุม เทียบกับที่วางแผนไว้ ทั้งหมด ไม่ได้วัดจากเวลาที่ใช้ครับ

ส่วนที่ยังไม่ครบคือการทดสอบกับ traffic จริง ซึ่งต้องรอ infrastructure

หมวดที่ 2 — คำถามเรื่องเทคนิค

ถาม: ทำไมเลือกให้คะแนนแบบสะสม ไม่ตัดสินทีเดียว

ตอบ: เพราะการโจมตีจริงมักไม่เกิดจากเหตุการณ์เดียวครับ

ผู้โจมตีทั่วไปจะสแกนหาช่องโหว่ก่อน แล้วจึงเจาะเข้าไป ถ้าตัดสินแค่ เหตุการณ์เดียว จะแยกไม่ออกระหว่างผู้ใช้ที่พิมพ์ URL ผิดกับผู้โจมตีที่ สแกนมาก่อนแล้วลองเข้า path ที่อ่อนไหว

ระบบคะแนนสะสมทำให้ IP ที่มีประวัติน่าสงสัยถึงเกณฑ์เร็วกว่า IP ที่เพิ่ง เข้ามาครั้งแรก และการลดคะแนนตามเวลาทำให้ผู้ใช้ที่ผิดพลาดครั้งเดียว กลับมาใช้งานปกติได้เองโดยไม่ต้องรอปลดบล็อก

ถาม: ทำไมเลือกเกณฑ์ 40 คะแนนสำหรับ redirect

ตอบ: มาจากการคำนวณย้อนกลับจากพฤติกรรมที่ต้องการให้ระบบตอบสนองครับ

เหตุการณ์ severity 1 บน HTTP ได้ 35 + 5 = 40 คะแนน ซึ่งควรถูก redirect เพราะ severity 1 หมายถึงพฤติกรรมที่ชัดเจนว่าเป็นการโจมตี

ส่วนเหตุการณ์ severity 3 บน HTTP ได้ 12 + 5 = 17 คะแนน อยู่ในช่วงเฝ้าดู ไม่ถึงขั้น redirect เพราะอาจเป็นผู้ใช้ปกติ

ค่านี้ตั้งใน config file แก้ได้โดยไม่ต้องแก้โค้ด และควรปรับหลังจากได้ ข้อมูลจริงจากการทดสอบกับ traffic บนเครือข่ายแล็บแล้ว

ถาม: การเชื่อมโยงข้ามโปรโตคอลทำงานอย่างไร

ตอบ: ระบบเก็บสถานะของแต่ละ IP ไว้ว่าเคยทำอะไรภายใน 30 นาทีที่ผ่านมาครับ

เมื่อพบการสแกนจาก IP หนึ่ง ระบบบันทึกเวลาไว้ ถ้า IP เดิมกลับมาเรียกเว็บ ภายใน 30 นาที จะได้คะแนนเพิ่ม 20 คะแนน เพราะพฤติกรรม "สแกนแล้วเข้าเว็บ" น่าสงสัยกว่าการเข้าเว็บเปล่าๆ

ตัวอย่างการคำนวณ ถ้า IP สแกนก่อนแล้วเรียกเว็บด้วย severity 2 จะได้ 25 + 5 + 20 = 50 คะแนน ถึงเกณฑ์ redirect ขณะที่ถ้าไม่มีประวัติสแกน จะได้แค่ 25 + 5 = 30 คะแนน อยู่ในช่วงเฝ้าดู

โค้ดส่วนนี้อยู่ใน defender/decision_engine/adaptive_defender/risk.py

ถาม: ถ้าโปรแกรมหยุดกลางทาง ข้อมูลจะหายไหม

ตอบ: ไม่หายครับ ระบบใช้ checkpoint บันทึกสองค่าคือ inode ของไฟล์และ ตำแหน่ง byte ที่อ่านถึง

เมื่อเริ่มโปรแกรมใหม่ ระบบอ่านค่าจาก checkpoint แล้วกระโดดไปตำแหน่งเดิม ทำให้ไม่อ่านซ้ำและไม่ข้าม

กรณีที่ Suricata หมุนไฟล์ log ระบบตรวจจับได้จาก inode ที่เปลี่ยนไป แล้วเริ่มอ่านไฟล์ใหม่จากต้น มีเทสต์ยืนยันพฤติกรรมนี้

ถาม: ทำไมต้องใช้ atomic write

ตอบ: ป้องกันปัญหา race condition ครับ

ถ้าเขียนทับไฟล์ config โดยตรง มีช่วงเวลาที่ไฟล์เขียนไม่เสร็จ ถ้า Nginx อ่านไฟล์ในจังหวะนั้นจะได้ config ที่ไม่สมบูรณ์และอาจ crash

วิธีที่ใช้คือเขียนลงไฟล์ชั่วคราวในโฟลเดอร์เดียวกันให้เสร็จก่อน แล้วใช้ คำสั่ง rename ซึ่งระบบไฟล์รับประกันว่าเป็น atomic operation คือเสร็จ หรือไม่เสร็จเท่านั้น ไม่มีสถานะกลาง

ถาม: ทำไม Dashboard ผูกกับ 127.0.0.1 เท่านั้น

ตอบ: เพราะ Dashboard แสดงข้อมูลที่อ่อนไหวครับ ทั้ง IP ผู้โจมตี รูปแบบ การตรวจจับ และการตัดสินใจของระบบ

ถ้าผูกกับ 0.0.0.0 ผู้โจมตีที่เข้าถึงเครือข่ายได้จะเห็นว่าระบบตรวจจับอะไร และปรับพฤติกรรมเพื่อหลบเลี่ยง

โค้ดมีการตรวจสอบที่ปฏิเสธการผูกกับ IP อื่นและโยน exception ทันที มีเทสต์ยืนยันว่าการตั้งค่า 0.0.0.0 ถูกปฏิเสธ

การเข้าใช้จากเครื่องอื่นต้องใช้ SSH port forwarding ซึ่งปลอดภัยกว่า เพราะมีการยืนยันตัวตนและเข้ารหัส

หมวดที่ 3 — คำถามเรื่องความน่าเชื่อถือของผลทดสอบ

ถาม: ความแม่นยำ 1.0 เชื่อถือได้แค่ไหน

ตอบ: ยังเชื่อถือไม่ได้ครับ และผมระบุข้อจำกัดนี้ไว้ในรายงานชัดเจน

ค่านี้มาจากชุดข้อมูลสังเคราะห์เพียง 4 รายการที่สร้างขึ้นเพื่อทดสอบว่า โค้ดคำนวณถูกต้อง ไม่ใช่เพื่อวัดประสิทธิภาพจริง

การจะได้ค่าที่อ้างอิงได้ต้องทดสอบกับ traffic จริงบนเครือข่ายแล็บที่ได้รับ อนุญาต มีจำนวนตัวอย่างมากพอ และครอบคลุมรูปแบบการใช้งานที่หลากหลาย ซึ่งเป็นงานที่รอ infrastructure พร้อม

ถาม: ทำไมบางเฟสเขียนว่า NOT_RUN ไม่เขียนว่าผ่าน

ตอบ: เพราะการทดสอบนั้นยังไม่ได้รันจริงครับ

โปรเจคนี้ใช้กฎว่าไม่ใช้คำว่า PASSED กับสิ่งที่ยังไม่ได้ทดสอบ เพราะรายงาน ที่บอกว่าผ่านทั้งที่ยังไม่ทดสอบจะทำให้ตัดสินใจผิดในขั้นต่อไป

และในบริบทความปลอดภัย การเข้าใจผิดว่าระบบทำงานได้ทั้งที่ยังไม่ได้ยืนยัน เป็นความเสี่ยงโดยตรง

ตัวอย่างเช่น D3 มี 8 rules แต่ยืนยันด้วย alert จริงได้แค่ 2 rules ที่เหลือผ่านแค่การตรวจ syntax จึงรายงานตามความจริงว่าอีก 6 rules ยัง NOT_RUN

ถาม: rule ที่ผ่านแค่ syntax มีประโยชน์อะไร

ตอบ: บอกได้ว่า Suricata อ่าน rule นั้นได้และจะไม่ทำให้ service ล่ม เมื่อโหลดครับ ซึ่งเป็นเงื่อนไขจำเป็นแต่ไม่เพียงพอ

สิ่งที่ยังไม่รู้คือ rule นั้นตรวจจับสิ่งที่ต้องการได้จริงหรือไม่ และจะ แจ้งเตือนผิดพลาดกับ traffic ปกติหรือไม่ ต้องสร้าง PCAP ทดสอบสำหรับ แต่ละ rule เพิ่ม ซึ่งเป็นงานที่วางแผนไว้แล้ว

หมวดที่ 4 — คำถามเรื่องการออกแบบ

ถาม: ทำไมแยกเครือข่ายเป็นสองชั้น

ตอบ: เพื่อไม่ให้ผู้โจมตีเข้าถึง honeypot ได้โดยตรงครับ

ทุก traffic ต้องผ่าน Defender ทำให้ควบคุมและบันทึกได้ทั้งหมด และถ้า ผู้โจมตีหลุดออกจาก honeypot ได้ จะติดอยู่ในเครือข่าย inner ที่ไม่มี default route ออกไปไหนไม่ได้

การออกแบบนี้เรียกว่า containment คือจำกัดความเสียหายให้อยู่ในวงแคบ

ถาม: ทำไมต้องมี 5 ประตูตรวจสอบสำหรับ rule ใหม่

ตอบ: เพราะ rule ที่ได้จากการวิเคราะห์อัตโนมัติอาจมีปัญหาได้หลายแบบครับ

ประตูที่ 1 กัน rule ที่ syntax ผิดซึ่งจะทำให้ Suricata ไม่ทำงาน ประตูที่ 2 กัน SID ซ้ำที่จะทำให้เกิดความสับสนในการวิเคราะห์ ประตูที่ 3 กัน rule ที่กว้างเกินไปจนแจ้งเตือนผิดพลาดกับ traffic ปกติ ประตูที่ 4 ยืนยันว่า rule ตรวจจับสิ่งที่ต้องการได้จริง ประตูที่ 5 กัน rule ที่ทำให้ระบบทำงานช้าเกินไป

ถ้าไม่มีการตรวจเหล่านี้ ระบบที่เรียนรู้เองอาจสร้าง rule ที่ทำให้ระบบ แย่ลงกว่าเดิม

ถาม: ถ้า honeypot ล่ม ระบบจะทำอย่างไร

ตอบ: Nginx config มีการจัดการกรณีนี้ครับ ถ้า backend ไม่ตอบสนอง จะคืน HTTP 503 พร้อมข้อความที่ควบคุมได้ ไม่แสดงหน้า error มาตรฐาน ที่อาจเปิดเผยว่าเป็นระบบ honeypot

ตั้ง timeout ไว้สั้นคือเชื่อมต่อ 2 วินาที และอ่านข้อมูล 5 วินาที เพื่อไม่ให้ค้างนาน

ถาม: ทำไมค่าตั้งต้นเป็น dry-run

ตอบ: เพื่อความปลอดภัยครับ ในโหมด dry-run ระบบคำนวณและบันทึกว่าจะทำอะไร แต่ไม่สั่งการจริง

ทำให้ทดสอบตรรกะได้โดยไม่กระทบระบบ และตรวจสอบได้ว่าคำสั่งที่จะสั่งถูกต้อง ก่อนเปิดใช้จริง ซึ่งสำคัญมากสำหรับระบบที่แก้ไข firewall เพราะความผิดพลาด อาจทำให้เข้าเครื่องไม่ได้

หมวดที่ 5 — คำถามเรื่องการทำงานร่วมกัน

ถาม: การประสานงานกับคนที่ 2 เป็นอย่างไร

ตอบ: กำหนดรูปแบบข้อมูลที่ต้องแลกเปลี่ยนเป็น JSON schema ไว้ใน docs/person2-contract.md ครับ ระบุชัดว่าต้องการค่าอะไรและรูปแบบไหน

วิธีนี้ทำให้ทั้งสองฝ่ายทำงานขนานกันได้โดยไม่ต้องรอกัน เพราะรู้ล่วงหน้าว่า ข้อมูลที่จะได้รับมีหน้าตาอย่างไร

ระบบตั้งค่าตั้งต้นว่าไม่ถือว่า endpoint ใดพร้อมใช้จนกว่าจะได้ค่าจริง และตรวจสอบผ่านเครือข่าย inner แล้ว เพื่อไม่ให้เกิดการสมมติที่ผิดพลาด

ถาม: ถ้าคนที่ 2 ส่งข้อมูลมาช้า จะกระทบไหม

ตอบ: กระทบเฉพาะการทดสอบ end-to-end ครับ ส่วนที่พัฒนาได้เองทำไปแล้ว ทั้งหมด

การออกแบบใช้ template ที่มี placeholder ทำให้เมื่อได้ค่าจริงมาแล้ว แค่แทนค่าลงไปก็ใช้งานได้ ไม่ต้องแก้โครงสร้าง

หมวดที่ 6 — คำถามเชิงลึก

ถาม: ระบบนี้ป้องกันการโจมตีแบบ distributed ได้ไหม

ตอบ: ปัจจุบันยังไม่ได้ครับ เพราะระบบเก็บคะแนนแยกตาม IP ถ้าผู้โจมตีใช้ หลาย IP แต่ละ IP จะสะสมคะแนนไม่ถึงเกณฑ์

การแก้ต้องเพิ่มการวิเคราะห์ระดับ subnet หรือดูรูปแบบพฤติกรรมที่คล้ายกัน ข้าม IP ซึ่งเป็นงานที่อยู่นอกขอบเขตเฟสปัจจุบัน แต่บันทึกไว้เป็นข้อจำกัด ที่ทราบแล้ว

ถาม: ถ้าผู้โจมตีรู้ว่ามีระบบนี้ จะหลบได้ไหม

ตอบ: หลบได้ในระดับหนึ่งครับ วิธีที่เป็นไปได้คือโจมตีช้าๆ ให้คะแนน ลดลงเร็วกว่าที่สะสม หรือใช้ User-Agent ปกติ

การรับมือคือปรับค่า decay ให้ช้าลง และเพิ่ม rule ที่ตรวจจับพฤติกรรม ระยะยาว ซึ่งต้องอาศัยข้อมูลจริงจึงจะปรับได้เหมาะสม

ข้อจำกัดนี้เป็นเรื่องปกติของระบบตรวจจับทุกแบบ ไม่มีระบบใดป้องกันได้ สมบูรณ์ เป้าหมายคือเพิ่มต้นทุนให้ผู้โจมตีและเก็บข้อมูลพฤติกรรม

ถาม: ทำไมเลือก Suricata ไม่ใช่ตัวอื่น

ตอบ: เหตุผลหลักคือ Suricata เขียน log เป็น JSON บรรทัดต่อบรรทัด ในไฟล์ eve.json ซึ่งอ่านและแปลงเป็นข้อมูลได้ง่ายโดยไม่ต้องเขียน parser ซับซ้อนครับ

นอกจากนี้รองรับการวิเคราะห์ระดับ application protocol ทำให้เขียน rule ตรวจจับ HTTP path หรือ TLS metadata ได้โดยตรง และติดตั้งอยู่บนเครื่องแล้ว เวอร์ชัน 7.0.3

ถาม: ระบบนี้นำไปใช้งานจริงได้เลยไหม

ตอบ: ยังไม่ได้ครับ และไม่ควรนำไปใช้ในสภาพปัจจุบัน

เหตุผลคือยังไม่ผ่านการทดสอบกับ traffic จริง ค่าเกณฑ์ต่างๆ ยังไม่ได้ปรับ จากข้อมูลจริง และยังไม่ได้ทดสอบการกู้คืนบนระบบจริง

ระบบนี้ออกแบบสำหรับสภาพแวดล้อมแล็บที่แยกออกมา เพื่อศึกษาพฤติกรรม ผู้โจมตีและทดสอบแนวคิด การนำไปใช้จริงต้องผ่านการทดสอบและปรับแต่ง อีกมาก รวมถึงการตรวจสอบด้านความปลอดภัยโดยผู้เชี่ยวชาญ

สรุปประเด็นสำคัญสำหรับการนำเสนอ

หากมีเวลาจำกัด ควรเน้นสามประเด็นนี้

ประเด็นที่ 1 ระบบใช้การให้คะแนนแบบสะสมและเชื่อมโยงข้ามโปรโตคอล ทำให้แยกผู้โจมตีจากผู้ใช้ปกติได้ดีกว่าการตัดสินครั้งเดียว

ประเด็นที่ 2 ส่วนซอฟต์แวร์เสร็จและทดสอบผ่าน 17/17 มีหลักฐานเก็บไว้ ครบ ส่วนที่ยังไม่เสร็จติดขัดที่ infrastructure ไม่ใช่ตัวโค้ด

ประเด็นที่ 3 รายงานทุกสถานะอ้างอิงหลักฐานจริง ไม่ใช้คำว่าผ่านกับ การทดสอบที่ยังไม่ได้รัน และระบุข้อจำกัดของตัวเลขที่วัดได้อย่างชัดเจน
